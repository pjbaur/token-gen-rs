01

Choose the right token

Start from the job the token must perform. Each type encodes different lifecycle and verification assumptions.

What are you building?

Recommended

Auth token

Use random bearer tokens, optionally HMAC-signed with an embedded expiry.

token-gen auth -x 3600

Needs TOKEN_GEN_SECRET (or -s) — see CLI workflows below.

Auth

Opaque by default

A random Base64URL or hex value. Add an expiry and an HMAC signature when temporary access must be self-validating.

API key

Readable prefix

The key type and environment remain visible—such as sk_test_…—while the secret body stays random.

CSRF

Session-bound

An HMAC signature covers the timestamp, nonce, and session ID. A different session means verification fails.

The crate currently installs from a local checkout. The library carries no CLI dependencies unless the cli feature is enabled.

Confirm toolchain

Install the executable globally, add a path dependency to an application, or do both.

03

CLI workflows

Three subcommands cover generation and verification. Defaults: 32 random bytes, one result, plain output.

Keep signing secrets out of command history.

--secret exists for development. Prefer TOKEN_GEN_SECRET loaded from a password manager or a silent prompt.

bash/zsh · secret setup
printf 'Secret: '
read -r -s TOKEN_GEN_SECRET
export TOKEN_GEN_SECRET

Auth tokens

Use a simple token when the application stores token state. Use an expiring token when the receiver must validate the signature and deadline. --format/-f applies only to simple tokens — expiring tokens are always Base64URL.

shell · auth
# 32 random bytes, Base64URL
token-gen auth

# 64 random bytes, hex, three results
token-gen auth --length 64 --format hex --count 3

# HMAC-signed token expiring in one hour
SIGNED_TOKEN="$(token-gen auth --expires-in 3600)"

# Expiry inspection (does not verify signature)
token-gen auth --check-expiry "$SIGNED_TOKEN"
expiry timestampBase64URL.random nonceBase64URL.HMAC signatureBase64URL
--check-expiry answers only “past deadline?”

It does not authenticate the signature. In Rust applications, call AuthToken::verify(&secret) before trusting the token. A token with no . separators — including random garbage — is treated as a never-expiring simple token and reports expired: false rather than an error.

API keys

Generation returns the raw key plus a SHA-256 hash. Deliver the raw key once; store the hash. The prefix communicates the intended type and environment.

skKey type_testEnvironment_mY8k…Random body
shell · API keys
# Default: api_live_… plus storage hash
token-gen api

# Secret key for test environment
token-gen api --key-type sk --env test

# Automation-friendly JSON
token-gen api --count 5 --output json

# Hash existing key, then verify against stored hash
token-gen api --hash "$API_KEY"
token-gen api --verify "$API_KEY" "$API_HASH"
Flag valueMeaningExample prefix
apiGeneral API credentialapi_live_
skSecret/server-side credentialsk_test_
pkPublic/publishable identifierpk_staging_

CSRF tokens

Generation and verification require the same secret and the exact same session ID. Default maximum verification age: 3,600 seconds.

shell · CSRF
SESSION_ID="user-session-123"
CSRF_TOKEN="$(token-gen csrf --session-id "$SESSION_ID")"

token-gen csrf \
  --session-id "$SESSION_ID" \
  --verify "$CSRF_TOKEN" \
  --max-age 3600

JSON output

OperationSingle-result shape
Auth / CSRF generation{"token":"…"}
API generation{"key":"…","key_hash":"sha256:…"}
API / CSRF verification{"valid":true}
Auth expiry check{"expired":false}
API key hashing (--hash){"hash":"…"}

Running any generation command with --count/-n greater than one wraps the single-result shape in an envelope instead: {"tokens":[…]}.

Verification and expiry checks always exit 0.

api --verify, csrf --verify, and auth --check-expiry report the result in their output (valid: false, expired: true) but the process exits successfully either way. Automation must parse output rather than rely on exit status.

04

Rust library

Distinct token types prevent accidental interchange. Builders validate the configuration when generate() runs.

Generate auth token

rust
// Random bearer token
use token_gen::{AuthToken, Format};

let token = AuthToken::generate(32, Format::Base64Url)?;
println!("{token}");

Generate and verify expiring auth token

01 · ISSUESign

The expiry timestamp and random nonce receive an HMAC-SHA256 signature.

02 · TRANSPORTSend

Treat the complete token as a bearer credential over a protected channel.

03 · ACCEPTVerify

Validate the signature and expiry using the same secret.

rust
use std::time::Duration;
use token_gen::{AuthToken, SecretKey};

let secret = SecretKey::from_string(
    "replace-with-a-random-secret-at-least-16-bytes",
)?;

let token = AuthToken::builder()
    .length(32)
    .expires_in(Duration::from_secs(3600))
    .secret_key(&secret)
    .generate()?;

token.verify(&secret)?; // signature + expiry

Issue API key safely

rust
// send_once_to_user, store_in_database, request_key, stored_hash:
// placeholders for your application code.
use token_gen::{ApiKey, ApiKeyType, Environment, HashAlgorithm};

let generated = ApiKey::builder()
    .key_type(ApiKeyType::Secret)
    .environment(Environment::Live)
    .hash_algorithm(HashAlgorithm::Scrypt)
    .generate_with_hash()?;

send_once_to_user(generated.key.as_str());
store_in_database(&generated.key_hash);

// On later request:
let presented: ApiKey = request_key.parse()?;
assert!(presented.verify(&stored_hash));
SHA-256 or scrypt?

Both support constant-time verification. SHA-256 is fast and is the CLI default. Scrypt adds a work factor and a random salt; select it through the Rust builder.

Bind CSRF token to session

rust
use token_gen::{CsrfToken, SecretKey};

let secret = SecretKey::from_string(
    "replace-with-a-random-secret-at-least-16-bytes",
)?;
let session_id = "user-session-123";

let token = CsrfToken::generate(&secret, session_id, 32)?;
let claims = token.verify(&secret, session_id, 3600)?;

assert_eq!(claims.session_id, session_id);

Error handling

Fallible operations return Result<_, TokenError>. Propagate with ?, or match variants when the caller needs a specialized response.

rust
// Handler functions are placeholders for your application code.
use token_gen::TokenError;

match token.verify(&secret) {
    Ok(()) => accept_request(),
    Err(TokenError::Expired) => ask_for_fresh_token(),
    Err(TokenError::InvalidSignature) => reject_request(),
    Err(error) => log_validation_error(error),
}
05

Security model

The library supplies cryptographic primitives and safe lower bounds. The application still owns secret storage, delivery, rotation, authorization, and revocation.

  • OS-backed CSPRNG through SysRng
  • Minimum 16 random bytes per token
  • HMAC-SHA256 signed auth and CSRF tokens
  • Constant-time signature and hash comparison
  • API keys redact secret body in Debug
  • Signing keys require at least 16 bytes

Production checklist

DoWhy
Generate signing secrets with a secure secret managerHuman-chosen strings often contain less entropy than their length suggests.
Store only API key hashesDatabase disclosure should not reveal working bearer credentials.
Show the raw API key onceReduces copies across logs, support tools, and later responses.
Use TLS for token transportBearer tokens grant access to anyone who captures them.
Pair prefixes with server-side authorizationpk_ or sk_ labels communicate intent; they do not enforce permission.
Design rotation and revocationCryptographic validity alone cannot disable a compromised credential.
Never log raw tokens, keys, or signing secrets.

CLI output intentionally contains credentials. Keep terminal capture, CI logs, shell tracing, and copied JSON in mind.

07

Troubleshooting

Most failures point to a missing secret, a mismatched verification context, or a length below the security floor.

“Secret required”

Expiring auth generation and every CSRF operation need a signing secret. Export TOKEN_GEN_SECRET, or use the development-only --secret. Minimum: 16 UTF-8 bytes.

“Insufficient entropy”

--length is a random-byte count, not an output character count. Set 16 or higher; the default of 32 is recommended.

CSRF verification prints valid: false

Confirm the same secret, the exact same session ID, and an acceptable --max-age. Any mismatch invalidates the token.

API verification prints valid: false

Pass the raw key first and the complete stored hash second. The hash must retain its algorithm prefix—sha256: or scrypt:.

token-gen: command not found

Install with cargo install --path /path/to/token-gen-rs --features cli, then ensure the Cargo bin directory appears on PATH.

Need the exact current flags

Run token-gen --help or token-gen <auth|api|csrf> --help. CLI help remains authoritative for the installed build.
